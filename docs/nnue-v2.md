# NNUE v2: четыре king buckets

V2 сохраняет размер аккумулятора 256, два i16-набора сумм и CReLU, а также
выход 512 → 1 с прежним масштабом 400 cp. Добавляется выбор одного из четырёх
наборов весов первого слоя по положению собственного короля каждой перспективы.
Зеркалирование файлов, SCReLU и отдельные выходы по материалу остаются
самостоятельными последующими экспериментами.

Контрольное обучение и две первоначальные серии матчей завершены.
Преимущество v2 над исходной v1 пока не установлено уверенно;
рекомендованная первая игровая сеть остаётся v1.

## Индексация и обновления

Клетка короля нормализуется по цвету: `square ^ 56` для чёрных, без изменения
для белых. Номер группы:

```text
bucket = (file >= e) + 2 * (relative_rank >= 5)
feature = bucket * 768 + relative_piece_square_index
```

Четыре области: a1–d4, e1–h4, a5–d8, e5–h8 в координатах перспективы.
При смене группы пересчитывается только соответствующая половина аккумулятора
на **новой** доске. Для неё дельты старой группы больше не применяются.
Вторая половина продолжает получать обычные удаления/добавления.
Рокировка может менять группу, null move не меняет её. Произвольные FEN resets,
возврат к родителю и пропущенные поиском промежуточные позиции поддерживаются.

`nnue_refreshes` считает полные создания кадров поиска; отдельный
`nnue_bucket_refreshes` считает пересчёты отдельных перспектив при смене группы.
Оба счётчика видны в UCI-диагностике и бенче. Смена активной сети по-прежнему
очищает TT, raw eval cache, histories и SMP-состояние.

## Формат и численные границы

V1 читается и экспортируется в прежнем виде, включая точное совпадение старых
golden-позиций. `FILE_BYTES`/`FORMAT_VERSION` остаются константами v1;
для v2 добавлены `V2_FILE_BYTES`/`FORMAT_VERSION_V2`. Методы модели возвращают
её фактическую версию, число групп и размер.

Заголовок v2 сохраняет magic `ZNNUE\0\0\0` и размер 64 байта. Восемь u32
с offset 8: `[2, 768, 256, 1, 255, 64, 400, 4]`. Далее остаются размер payload
по offset 40, FNV-1a64 по offset 48 и нулевой reserved u64 по offset 56.
Checksum считается по всему файлу с обнулёнными собственными байтами.

Payload: общий bias первого слоя (256 i16), четыре последовательные банки
весов (каждая 768×256 i16, feature-major), общий выход (512 i16), bias выхода
(i32). Итого **1 574 468 байт**, около 1.50 MiB. Загрузка ограничена этим размером,
проверяет точные размеры, поля и checksum перед созданием модели; ограничения
каждого параметра проверяются во всех четырёх банках.

Границы i16-сумм не увеличиваются: одна перспектива использует только одну
банку и максимум 32 активных признака. Полный пересчёт начинает с общего bias,
а инкрементальные операции удаляют фигуры перед добавлением.

## Тренер и начальные веса

`train_nnue.py --king-buckets 4` выбирает v2; без флага остаётся v1. Короли
извлекаются из тех же 100-байтных записей, binpack и train/validation split
не изменяются. Позиции группируются по банкам: тренер вычисляет только выбранные
веса, без тензора весов на каждую позицию и без четырёх полных проходов для неё.

`--init-model` из v1 повторяет её веса во всех четырёх банках, переносит общие
bias и выход. Квантованные оценки до первого шага обучения совпадают **точно**
с исходной сетью. Это проверяется на обеих перспективах и всех четырёх группах.
Начальная validation и экспорт сохраняются отдельно. Оптимизатор/schedule при
этом новые; `--resume` продолжает точный checkpoint, а обратное сворачивание
v2 → v1 не допускается автоматически.

## Выполненные проверки

Прошли 155 Rust-тестов обычного `cargo test --all-targets`, clippy с запретом
предупреждений и release-сборка. Отдельные проверки v2 покрывают границы групп,
обе рокировки, взятие королём через границу, EP, promotion, null move, undo,
случайные ветвления/сбросы FEN, строгий формат и ограничения последней банки.
Проверены загрузка/отклонение моделей, SMP, MultiPV и переключение оценки.

В Python прошли 21 различные проверки пайплайна, включая v1/v2 transfer,
градиенты только выбранной банки, независимый NumPy oracle, экспорт и точный
CPU resume. CUDA-пилот прошёл две эпохи по 1 048 576 позиций на префиксе T80;
это проверка совместимости/скорости, а не доказательство силы сети.
Его экспорт совпал на 1000 позициях в trainer/NumPy/Rust scalar/AVX2;
два прохода по 4096 позициям случайной игры дали одинаковые scalar/AVX2-выводы
и совпадение delta/refresh/dense. Реальная сеть проверена с Threads=8 и
MultiPV=5 на трёх позициях, все 15 PV легальны.

До дообучения клонированная v2 и исходная v1 прошли идентичные деревья поиска
на пяти позициях при depth=10: 2 361 365 узлов в каждом прогоне, одинаковые
оценки и лучшие ходы. [Четыре парных замера с чередованием порядка](../games/zenith-nnue-v2-clone-bench.json)
сохраняют SHA бинарника и обеих сетей. Локальные тайминги заметно колеблются;
по этим измерениям не делается вывод о приросте скорости или силы.

## Контрольный эксперимент

Обе ветви завершили по 24 эпохи и получили по 201 326 592 дополнительных
предъявления позиций. V2 обучалась 1747 секунд, контрольная v1 — 1655 секунд.
Лучший экспорт v2 выбран на эпохе 20 (quantized validation loss 0.01055857),
контрольной v1 — на эпохе 21 (0.01076053). Исходная v1 имела 0.01084087.
Это результаты на одной фиксированной validation-выборке, а не рейтинг Elo.

Первые парные матчи при 5s+0.05s, Threads=1, Hash=32 MiB, Syzygy выключена:

- V2 против v1 с тем же дополнительным обучением: **+58 =31 −39**, 128 партий.
  [PGN](../games/zenith-nnue-v2-vs-v1-control-20261027.pgn).
- V2 против исходной v1: **+47 =38 −43**, 128 партий.
  [PGN](../games/zenith-nnue-v2-vs-original-20261027.pgn).

Все партии независимо проверены, forfeits и ошибок легальности нет. Вторая
серия слишком близкая, чтобы объявлять существенный прирост над исходной сетью.
[Манифест с SHA моделей, метриками и результатами](../networks/king-buckets-control-20261027.json).
Более длинные серии 10s+0.10s запущены отдельно; их результаты в этот снимок
не включены. Веса, datasets и checkpoints остаются локально вне Git.

Команда воспроизведения (выходной каталог должен быть новым):

```powershell
./.venv-nnue-cuda/Scripts/python.exe -u tools/nnue/run_king_bucket_training.py --out runs/king-buckets-control-20261027
```

Обе ветви стартуют из проверенного `best.pt` первой v1. План: до 24 эпох по
8 388 608 принятых позиций, одинаковые seed=2, batch=8192, validation=131072,
sigmoid scale=200 и cosine LR 3e-4 → 1e-5. V2 имеет мягкий бюджет 30 минут
на обучение с завершением полной эпохи. Контроль v1 получает ровно столько же
эпох и то же исходное расписание; неравное число предъявлений блокирует матч.
Эти предъявления идут дополнительно к исходному обучению.

Существующий полный SHA-256-отчёт корпуса используется с проверкой размеров
и mtime. Изменённый после проверки файл блокирует запуск и требует повторного
хеширования. Во время обеих ветвей также контролируется неизменность корпуса.
Это кэш локальной проверки, а не аутентификация от намеренной подмены mtime.

Далее выполняются parity каждой сети на 1000 позициях и два матча по 128 партий:
v2 против v1 с тем же дополнительным обучением, затем v2 против исходной v1.
Контроль 5s+0.05s, Threads=1, Hash=32 MiB, парные дебюты из holdout-набора,
проверка легальности и forfeits. Это позволяет отделить эффект архитектуры от
эффекта дополнительного обучения. Проверки/матчи и подготовка данных идут
отдельно от бюджета GPU-обучения.

`status.json`, `plan.json`, `train-v2.log`, `train-v1-control.log` и файлы матчей
лежат в каталоге задачи. Чекпоинты — в `v2/` и `v1-control/`. Ошибка записывается
в статус и останавливает следующие стадии. Задача не заменяет рекомендованную
v1 автоматически: сначала оцениваются игровые результаты и неопределённость.
