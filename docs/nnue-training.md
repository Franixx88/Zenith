# Подготовка и обучение NNUE v1

Инструменты пользователя перенесены из Downloads в репозиторий и исправлены:
`examples/prepare_nnue.rs`, `tools/nnue/{parquet_to_tsv,train_nnue,check_parity,records}.py`.
Оригиналы в Downloads сохранены. Это пайплайн существующей архитектуры
768 → 256×2 → 1, а не готовая сильная игровая сеть. С 0.13.0 UCI умеет загрузить
экспорт через `EvalFile` и использовать его в поиске. Без файла остаётся
классическая оценка. [Подключение и переключение оценки](nnue-search-0.13.md).
Большие обучающие датасеты на этом этапе не скачивались.

## Окружение

Создана локальная `.venv-nnue`: Python 3.12.15, PyTorch 2.10.0+cpu,
NumPy 2.4.2, PyArrow 23.0.1, python-chess 1.999 (chess 1.11.2).
Прямые зависимости указаны в `tools/nnue/requirements.txt`, полный снимок CPU-
окружения — `requirements-cpu-lock.txt`. Это не системная установка Python.
Проверки выполняются на CPU. CUDA на обнаруженной GTX 1660 Ti не проверялась.

Воссоздание через uv:

```powershell
uv venv --python 3.12 .venv-nnue
uv pip install --python .venv-nnue/Scripts/python.exe --torch-backend cpu -r tools/nnue/requirements-cpu-lock.txt
```

В текущем workspace uv доступен также как `target/uv-tools/uv.exe`.
Служебный Python установлен в `target/python-runtimes`; после очистки `target`
это окружение нужно воссоздать. Данные в `data/nnue` и веса в `runs` исключены
из Git и расположены вне `target`.

## Parquet → записи

```powershell
cargo build --release --example prepare_nnue --example nnue
./.venv-nnue/Scripts/python.exe tools/nnue/parquet_to_tsv.py "D:/datasets/part-*.parquet" --stride 100 |
  ./target/release/examples/prepare_nnue.exe --out data/nnue/run1 --min-depth 20 --score-pov white --require-complete --source "mateuszgrzyb/lichess-stockfish-normalized@d83b3256d94a086f074a66db52f3a5b5d4c28847" --license "CC-BY-4.0; Mateusz Grzyb; source Lichess CC0"
```

Путь служит примером: Parquet-шарды нужно иметь локально. Glob раскрывается
скриптом и работает в PowerShell. Читаются ограниченные Arrow batches.
`--stride` берёт каждую N-ю исходную строку, с единым счётчиком между файлами;
это уменьшение объёма, а не гарантия репрезентативности. Список файлов сортируется,
schema каждого проверяется до вывода данных. Null cp/mate передаются пустыми полями.

Подготовщик использует только новый выходной каталог. Входной файл открывается
до создания каталога, файлы создаются с `create_new`, существующие и частичные
датасеты никогда не обнуляются. При ошибке остаётся `INCOMPLETE` или отсутствует
финальный `manifest.txt`; тренер такой набор не принимает. После flush/sync всех
шардов манифест публикуется атомарным переименованием.

Parquet-скрипт в конце пишет `#zenith-tsv-complete<TAB>число_строк`.
`--require-complete` требует этот маркер с правильным счётчиком: досрочный EOF
при сбое предыдущего процесса не превращается в готовый датасет.
Этот режим несовместим с намеренным ранним ограничением `--max-rows`.
Для вручную подготовленного TSV без маркера флаг можно опустить.

Формат записи — 100 байт: 12 little-endian u64 относительных битбордов,
i16 stm score, u8 depth и нулевой flags. Остальные правила:

- `--score-pov white` — default для согласованного Lichess-контракта;
  `stm` — для источника, уже приведённого к стороне хода. Перспективу нужно
  подтверждать по источнику, независимо от формата файла.
- Выбросы по cp **отбрасываются**, а не обрезаются; `VALUE_NONE=32002` не проходит
  разрешённый предел `--max-cp` (не более 30000). Mate/null исключаются.
- По умолчанию исключаются шах, terminal и положительный SEE у тактического хода;
  `--keep-tactical` отключает только последний фильтр. Проверка FEN остаётся строгой.
- Разделение train/validation хеширует ровно 96 байт входных признаков: одинаковые
  входы, в том числе цветовые зеркала и варианты прав рокировки, остаются в одном
  split. Это защита от точных совпадений входа, не разделение по партиям.
- И train, и validation должны быть непустыми. Манифест содержит источник,
  лицензию, уникальный ID, настройки и причины отбраковки.

На источник Lichess остаётся прежняя оговорка: проверить знак и шкалу меток
на исходных чёрных FEN перед массовым обучением. Имя normalized этого не доказывает.

## Обучение, продолжение, экспорт

```powershell
./.venv-nnue/Scripts/python.exe tools/nnue/train_nnue.py --data data/nnue/run1 --out runs/v1 --epochs 10 --threads 8
./.venv-nnue/Scripts/python.exe tools/nnue/check_parity.py --net runs/v1/best.znnue --records data/nnue/run1/val.bin --zenith-nnue target/release/examples/nnue.exe --count 500
```

Шарды читаются через read-only memmap. Перемешиваются файлы, затем блоки, затем
строки внутри блока. По умолчанию копируемый блок — 65536 записей (6.25 MiB),
а не целый многогигабайтный шард. Выборка validation также не загружает весь файл
и не строит перестановку всех его индексов. Память рабочих массивов зависит от
размера блока, batch и validation sample; кэш страниц ОС учитывается отдельно.
Обрезанные записи и неизвестные flags отвергаются.

Checkpoint хранит веса, Adam, шаг, эпоху, NumPy/PyTorch/CUDA RNG, всю историю
метрик и лучший экспорт. На каждой границе эпохи сохраняется тройка
`epoch-NNNN.{pt,znnue,json}`; `latest.json` атомарно фиксирует готовую тройку и
её SHA256. `last.*`, `best.*` и `provenance.json` — удобные атомарно обновляемые
имена. При прерывании сохранения можно использовать последнюю тройку,
указанную `latest.json`; отдельный файл не заменяется частично записанными байтами.

```powershell
./.venv-nnue/Scripts/python.exe tools/nnue/train_nnue.py --data data/nnue/run1 --out runs/v1 --epochs 10 --threads 8 --resume runs/v1/last.pt
```

Для точного resume плановые `--epochs`, batch, seed, настройки потерь, данные и
среда должны совпадать. Быстрая идентификация данных использует манифест,
имена/размеры/mtime файлов; это не полное криптографическое хеширование датасета.
`--stop-after-epochs N` позволяет остановиться на границе эпохи, сохранив исходный
общий LR schedule. Побитовое совпадение непрерывного и возобновлённого обучения
проверено на CPU с одним вычислительным потоком; для других устройств/сред оно
не обещается автоматически.

Для новой обучающей выборки или нового расписания используются новый выходной
каталог и `--init-model runs/v1/last.pt`: копируются веса, оптимизатор и schedule
начинаются заново. Случайно затереть существующий run без resume нельзя.
Provenance хранит источник/лицензию, аргументы, runtime, полную историю, SHA256
лучшей и последней сетей. Лицензия меток не подменяется автоматически на CC BY.

Parity проверяет непустую случайную выборку, белые и зеркальные чёрные FEN,
арифметику тренера, отдельный NumPy-расчёт и Rust scalar/автоматический SIMD.
Исходные FEN и знак меток дополнительно проверяются тестами конвертера —
сравнение экспортов само по себе этого не доказывает.

## Новые binpack-источники

Версии, размеры и опубликованные LFS SHA256 сохранены в
`tools/nnue/dataset-sources.json`. Большие файлы **не скачаны**.
[Нативный потоковый reader](binpack-stream.md) реализован на `sfbinpack` 0.6.5
и подключён через `--binpack-config`. Это сжатый поток позиций/цепочек, не
наш массив 100-байтных записей; его нельзя передать как `train-*.bin`.
Проверка на одном полном блоке T91 не заменяет проверку целого корпуса
или калибровку шкалы его меток.

[T91 filtered](https://huggingface.co/datasets/adamtwiss/t91-binpacks-filtered):
12.62 GB, карточка указывает 4.44 млрд позиций и 3.08 млрд без skip-меток,
ODbL; skip имеет score 32002. Автор сообщает о более слабых сетях относительно
T80 и о вреде фильтрации в своих экспериментах. Это результат его архитектуры
и рецептов, не предсказание Elo Zenith. Набор разумно оставить кандидатом для
контролируемого сравнения, а не автоматически объявлять лучшим.
Перепаковка 3.08 млрд записей в наш формат заняла бы около 308 GB до собственных
дополнительных фильтров — прямое потоковое обучение/ограниченный импорт здесь важны.

`dfrc_n5000.binpack` — 37.48 GB, `T60T70wIsRightFarseer.binpack` — 32.98 GB;
оба доступны в [официальном master-binpacks](https://huggingface.co/datasets/official-stockfish/master-binpacks)
с лицензией ODbL по карточке. [Stockfish training wiki](https://github.com/official-stockfish/nnue-pytorch/wiki/Training-datasets)
описывает DFRC-происхождение первого и историческую смесь источников второго,
а также их совместное использование. DFRC требует проверки Chess960-рокировок:
наш строгий стандартный парсер нельзя молча ослаблять ради импорта.
Порядок SF-derived → Lc0-derived из wiki — гипотеза для отдельного эксперимента
на нашей сети, не установленный оптимальный рецепт.

## Проверки

```powershell
cargo clippy --all-targets -- -D warnings
cargo test --release --example prepare_nnue
cargo build --release --example prepare_nnue --example nnue
./.venv-nnue/Scripts/python.exe -m unittest discover -s tools/nnue -p test_pipeline.py -v
```

Smoke-тест создаёт временные данные с **синтетическими** метками, выполняет две
эпохи и точное resume, проверяет блокировку перезаписи, пустые/повреждённые данные,
сбой TSV-производителя, исходные FEN/метки/split и экспорт. В
`target/nnue-pipeline-smoke` остаются только демонстрационная `best.znnue`,
provenance и parity-лог. Эта сеть не подключается к игре и не является оценкой Elo.

Проверено 2026-10-25: **2 Rust-теста и 7 Python-тестов прошли**, release examples
собраны, fmt и Clippy чистые. Непрерывные две эпохи и остановка/resume дали
одинаковые веса, историю validation и экспорт. Parity на 32 записях × 2 цвета
подтвердила все 64 позиции: trainer = NumPy spec = Rust scalar = Rust AVX2;
внутри Rust также совпали delta, refresh и dense reference.
