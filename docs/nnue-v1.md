# NNUE v1 — архитектура и формат, актуально для Zenith 0.13.0

Реализованы признаки, скалярный inference, квантование, формат весов и
инкрементальные аккумуляторы. Подготовка Parquet/binpack и PyTorch-тренер готовы;
с 0.13.0 сеть подключается к поиску через `EvalFile`. Обученных весов пока нет,
по умолчанию работает классическая оценка. Тестовые сети не загружаются
автоматически. [Интеграция в поиск](nnue-search-0.13.md).
Сети Stockfish и Reckless не совместимы с этим форматом.

## Архитектура и контракт обучения

Общая матрица признаков `768 × 256`, общий bias `256`, две перспективы.
Для каждой перспективы активен один признак на каждую фигуру, включая королей.
Порядок типов: pawn, knight, bishop, rook, queen, king. Клетки: a1=0, h8=63.

```text
relative_color = 0 для своих фигур, 1 для чужих
relative_square = square XOR (56 для чёрной перспективы, иначе 0)
feature = (relative_color * 6 + piece_type) * 64 + relative_square
A[p] = feature_bias + SUM(feature_weights[feature, :])
X = concat(clamp(A[side_to_move], 0, 255), clamp(A[opponent], 0, 255))
raw = output_bias + dot(X, output_weights)
cp = clamp(trunc_towards_zero(raw * 400 / (255 * 64)), -28000, 28000)
```

Матрица хранится **feature-major**, а не как стандартный PyTorch Linear
`[out_features, in_features]`. При экспорте Linear нужна транспозиция.
Конкатенация идёт по стороне хода, не фиксированно white/black. Поэтому смена
стороны хода не обязана давать точное отрицание прежнего значения: сеть может
учить темп. Отражение рангов вместе со сменой цветов сохраняет признаки.

Первая версия не использует king buckets, зеркалирование файлов, HalfKP,
SCReLU, дополнительные скрытые слои, PSQT skip или смешивание с классикой.
Это небольшая проверяемая архитектура, а не утверждение об оптимальном размере
или силе. King move меняет обычные признаки; полного refresh не требуется.
Рокировочные права, en passant и счётчики не входят в признаки. Терминальные
результаты, повторения и правило 50 ходов остаются ответственностью поиска.

Для плавающей модели:

```text
a[p] = clamp(float_bias + SUM(float_feature_weights), 0, 1)
float_output = float_output_bias + dot(concat(a[stm], a[other]), float_output_weights)
float_cp = float_output * 400
feature_bias/weights: round(float_value * 255)
output_weights: round(float_value * 64)
output_bias: round(float_value * 255 * 64)
```

`FloatParameters::quantize` принимает f32, умножает через f64 и округляет к
ближайшему, половины **от нуля**. Это отличается от ties-to-even в некоторых
библиотеках. NaN, infinity, неверные размеры и выход за диапазон отвергаются;
тихого насыщения параметров нет. Будущий тренер должен соблюдать те же правила
и проверять точность уже квантованной модели на валидации. Соответствие с
PyTorch проверяется инструментом `tools/nnue/check_parity.py`, который сравнивает
квантованный экспорт, независимую NumPy-реализацию и Rust scalar/SIMD.

## Обновление позиции и числовая безопасность

`Network` неизменяемая. `Accumulator<'net>` заимствует конкретную сеть и хранит
два массива **неклипованных** i16 сумм плюс снимок Board. Он не выделяет heap.
`update(&next_board)` сначала удаляет исчезнувшие piece-square признаки,
потом добавляет новые. Разности двенадцати bitboard учитывают EP, capture,
promotion и castling без второй реализации шахматных правил. Возвращаемый
`FeatureChanges` считает физические удаления/добавления, не обе перспективы.

Для ветвления можно клонировать аккумулятор; для undo — передать прежний Board.
Произвольный FEN reset тоже корректен. Null move меняет порядок двух перспектив
в выходном слое и снимок Board, без изменения сумм. С 0.13.0 поиск хранит ленивый
стек состояний каждого потока на каждом main/qsearch ply. Он поддерживает
повторный поиск, отмену, null move и проверку исключённого хода.

При загрузке/создании проверяются абсолютные границы: FT weights ≤512,
FT biases ≤4096, output weights ≤8192, output bias ≤16 777 216.
При максимум 32 фигурах сумма по модулю ≤20 480. С 0.9.0 используем i16 для сумм
и i64 для итогового выхода, в том числе перед умножением на 400. Клипование применяется
только в выходном слое: сохранённые суммы не теряют информацию при undo.
Оценка ограничена ±28000, ниже матовой области поиска. С 0.9.0 доступны scalar
и runtime AVX2. Собственный unsafe изолирован в private NNUE kernels; веса v1
совместимы с 0.8.0. [Подробности и замеры](search-simd-0.9.md).

## Формат файла

Ровно **394 820 байт**, little-endian, заголовок 64 байта:

- 0..8: magic `ZNNUE\0\0\0`.
- Восемь u32 по смещениям 8,12,16,20,24,28,32,36: version=1,
  inputs=768, hidden=256, activation_id=1 (CReLU), QA=255, QB=64,
  centipawn_scale=400, feature_mapping_id=1.
- 40..48: u64 длина payload, 394756.
- 48..56: u64 FNV-1a64 всего файла; эти восемь байтов считаются нулевыми.
- 56..64: reserved u64=0.

Payload: 256 i16 FT biases, 768×256 i16 FT weights в feature-major порядке,
512 i16 output weights, один i32 output bias. Порядок output — stm, opponent.
FNV offset basis `0xcbf29ce484222325`, prime `0x100000001b3`, wrapping u64.
Это обнаружение повреждений, не криптографическая аутентификация.

Неизвестная архитектура/версия/масштаб/резерв, несовпадение размера/контрольной
суммы и параметры вне границ отвергаются. Загрузчик читает максимум размер v1+1
байт независимо от содержимого заголовка. Данные и архитектуру нельзя поменять
без нового идентификатора/версии. Происхождение обучающих данных, лицензия,
checkpoint, метрики и SHA-256 сети должны храниться отдельно при выпуске весов;
наличие правильного заголовка не подтверждает, что сеть обучена.

## Стенд и независимая проверка

```powershell
# Одноразовый синтетический fixture, не обученная сеть; существующий файл не затирается.
node tools/nnue_reference.cjs fixture target/synthetic-v1.znnue
cargo run --release --example nnue -- inspect target/synthetic-v1.znnue
cargo run --release --example nnue -- eval target/synthetic-v1.znnue "rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq -" e2e4 e7e5
cargo run --release --example nnue -- walk target/synthetic-v1.znnue 10000 > target/nnue-walk.tsv
node tools/nnue_reference.cjs verify target/synthetic-v1.znnue target/nnue-walk.tsv
cargo run --release --example nnue -- bench target/synthetic-v1.znnue 100000
cargo test --release --test nnue
```

`verify NETWORK` принимает FEN по одному на строку stdin, поддерживает 4 и 6
полей; пустые строки и комментарии `#` пропускаются. Невалидный FEN — ошибка с
номером строки. Выход `eval/verify/walk`: FEN, raw и cp, разделённые tab.
PowerShell может записать перенаправление в UTF-16: для Node-стенда нужен UTF-8
(например, `... | Set-Content -Encoding utf8 target/nnue-walk.tsv`).

Rust-стенд сравнивает delta, full refresh и отдельный dense reference. Node
независимо экспортирует формат и считает выход из FEN, не используя Rust-код.
Unit/integration tests проверяют также все lanes, branching/undo, повторения,
все четыре превращения с/без взятия за оба цвета, четыре рокировки, EP за оба
цвета, числа на границах, повреждения файлов, ориентацию и ручной пример.
Микробенчмарк сравнивает refresh+head и delta+head на одной последовательности
позиций с совпадающими checksum. Генерация ходов вне таймера; периодические
сбросы позиции внутри. Это не NPS поиска и не сравнение с классической оценкой.

Историческая проверка 0.8.0, 2026-10-24: 107 обычных release-тестов, fmt, Clippy и сборка прошли.
Node независимо подтвердил 10 000 позиций прохода и 22 отдельных эталона.
Три последовательных серии по миллиону оценок без параллельной компиляции:
refresh+head 2395.274 / 2425.555 / 2414.807 ms; delta+head
871.654 / 864.634 / 880.514 ms. Медианы 2.415 и 0.872 мкс/позицию,
отношение около 2.77. Одинаковая checksum −15081351800 во всех сериях.
Синтетическая сеть, ограниченный воспроизводимый набор; эти числа не
предсказывают скорость с обученной сетью в реальном поиске. Логи в игнорируемом
`target/nnue-stage1-bench-{1,2,3}.txt`. Контрольный классический bench 6 совпал
с финальным baseline `zenith-0.7.0-tuned.exe` по оценкам, ходам, всем счётчикам
и 364 220 узлам; непротестированный прирост силы не приписывается версии 0.8.

## Датасет Mateusz Grzyb

Источник: [lichess-stockfish-normalized](https://huggingface.co/datasets/mateuszgrzyb/lichess-stockfish-normalized),
revision `d83b3256d94a086f074a66db52f3a5b5d4c28847`, проверено 2026-10-24.
По карточке: **316 072 343** уникальных FEN, десять Parquet частей, примерно
6.56 GB хранилища (метаданные HF). По схеме viewer: `fen:string`, `depth:uint8`,
`cp:int16 nullable`, `mate:int8 nullable`. В названии normalized речь о
подготовке данных, **не о переводе cp в [0,1]**. Карточка описывает сохранение
максимальной глубины для одинакового FEN и удаление line/knodes; параметры
Stockfish, версия и WDL/результат партии отсутствуют. Весь набор не скачивался.

Лицензия производного набора — **CC BY 4.0**, атрибуция Mateusz Grzyb;
исходная [база Lichess](https://database.lichess.org/#evals) — CC0.
Метаданные сети и документация её обучения должны сохранять эту атрибуцию.

FEN содержит четыре поля. `parse_training_fen` дописывает `0 1` и применяет
обычную строгую проверку доски. Это неизвестные исторические счётчики, а не
восстановленная партия. Некоторые первые строки viewer имеют больше 16 фигур
за сторону; такой первый пример покрыт тестом и отвергается. Нужна фильтрация
стандартных, структурно допустимых позиций, а не ослабление правил движка.

У [Lichess eval-cache JsonView](https://github.com/lichess-org/lila/blob/master/modules/evalCache/src/main/JsonView.scala)
cp/mate выдаются из `pv.score.white`: перспектива **белых**. Карточка HF отдельно
знак не определяет и не описывает его преобразование. Рабочий контракт будущего
импортёра — white cp, перевод в stm cp знаком стороны; перед массовым обучением
нужно проверить это на отобранных чёрных позициях по исходной базе/учителю.
Само слово normalized не основание менять знак или шкалу.

Инструменты этапа 2 реализованы: потоковый Parquet → TSV → 100-байтные записи,
отчёт отбраковки, тренер, экспорт и parity. См. [запуск и проверки](nnue-training.md).
Массовая загрузка/обучение на этом датасете ещё не выполнялись. Первые N строк
не годятся как случайная выборка: просмотр начинается с лексикографически похожих FEN.
Одинаковые/цветосимметричные входы сети нельзя отдавать в разные splits.
Игровых идентификаторов нет: game/family split, применявшийся к нашим логам,
из этих четырёх колонок восстановить нельзя. Нужна воспроизводимая группировка
и отдельный внешний контроль качества; просто random split не доказывает
обобщение. Нынешние outcome CSV и новые cp-метки нельзя смешивать без явного
описания функции потерь.

Идеи аккумуляторов и квантования сверены с
[Stockfish NNUE docs](https://official-stockfish.github.io/docs/nnue-pytorch-wiki/docs/nnue.html).
Реализация и формат Zenith собственные; сторонние веса и исходники NNUE
не включены. Роста Elo на этом этапе не заявляется.
